- **PINNED ROOT CAUSE of the refresh stampede (3 concurrent refresh SOURCES, only ONE is gated):** the single-flight `_isRefreshing`/`_refreshToken$` gate in `refresh.interceptor.ts` ONLY guards interceptor 401s. `AuthService._doSilentRefresh()` (scheduled timer, auth.service.ts L190) and `AuthService.bootstrap()` (L124) call `authApi.refresh()` DIRECTLY, bypassing the gate. With refresh-token ROTATION (RefreshResponse rotates Set-Cookie per auth-api.service.ts L33-37), a timer refresh racing an interceptor refresh = 2 POSTs; rotation invalidates the loser → cascade 401 → logout hammer.
- **Secondary bugs found:** (1) `_refreshToken$` is never reset to null after a successful refresh (L89 leaves last token in the BehaviorSubject) — a LATE follower arriving in a NEW burst could `filter(!=null).take(1)` the STALE token before the leader's L73 `next(null)` lands → retries with a dead token → 401. (2) `_doSilentRefresh` catchError (L212) swallows failure silently — no logout, no single logout-once guard; on a genuine refresh-401 it neither logs out nor stops, so the next request 401s and re-triggers. (3) `scheduleRefresh` delayMs clamp is `Math.max(...,0)` (L108) — a dev TTL ≤30s yields delay=0 → immediate-refire loop (latent; NOT the 900s trigger but must fix). (4) interceptor module-level `let _isRefreshing` is reset on logout()? NO — it is never reset on logout, so a stuck `true` after an aborted refresh wedges all future 401s into the queue forever.
- **FIX DESIGN:** hoist the single-flight into AuthService as ONE shared in-flight `refresh()` Observable (shareReplay(1) / in-flight subject), and route ALL THREE sources (interceptor, _doSilentRefresh, bootstrap) through it. Reset in-flight + isRefreshing on BOTH success and error. Logout-once guard (idempotent logout already cancels timer; add a `_loggingOut` flag so cascade 401s call logout/navigate exactly once). Clamp scheduleRefresh delay to a sane MIN (e.g. 5000ms floor, and floor the (expiresIn-30) skew so tiny TTLs still leave a positive buffer).
